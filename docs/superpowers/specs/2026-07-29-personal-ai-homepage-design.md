# AI Nav 个人 AI 工具首页 MVP 设计

## 1. 产品定位

AI Nav 是面向个人用户的 AI 工具首页。它帮助用户把散落的 AI 工具链接快速收进一个地方，由系统自动补全信息和整理用途，并在需要时快速找到和打开。

MVP 验证的核心假设是：

> 如果添加工具几乎不需要整理成本，而且常用工具始终容易找到，用户会愿意把 AI Nav 设为日常入口。

目标用户是已经使用多个 AI 工具、但目前依赖浏览器书签、笔记或聊天记录保存链接的个人用户。

## 2. 目标与成功标准

### 目标

1. 用户能在一分钟内完成首次添加，并看到可用的工具首页。
2. 用户无需手工填写完整资料或设计分类体系。
3. 用户能通过常用区、用途分类或搜索，在几秒内找到目标工具。
4. 元数据提取或 AI 服务失败时，链接仍能成功保存和使用。

### MVP 验收标准

- 支持一次粘贴一个或多个 URL。
- 成功识别的 URL 自动获得标题、图标、简介和用途分类。
- 用户可在确认前修改自动生成的信息。
- 用户可搜索名称、域名、简介和分类。
- 用户可将工具加入或移出“常用”。
- 首页默认优先展示常用工具，其余工具按分类浏览。
- 数据保存在本地 SQLite 中，刷新和重启服务后不丢失。
- 桌面和移动端均能完成添加、查找、收藏和打开工具的完整流程。

不在 MVP 中使用留存率等长期指标作为发布门槛；发布后的首要观测指标是首次添加完成率、添加耗时和工具打开路径长度。

## 3. 方案选择

### 方案 A：智能收藏夹（采用）

围绕“添加、自动整理、快速打开”形成单一闭环。它最贴合个人用户的已有行为，也能最大程度复用当前项目的书签、分类、搜索和本地存储能力。

### 方案 B：AI 工具发现站

以推荐、榜单和工具详情为核心。它能解决“不知道用什么工具”的问题，但需要持续的数据采集、内容运营和推荐质量建设，不适合作为单人产品的最小验证版本。

### 方案 C：工作流启动器

让用户保存一组工具并一键启动某项工作。它有较强差异化，但需要先理解用户稳定的工作流模式，也依赖浏览器扩展或更深的系统集成。

因此 MVP 采用方案 A，并保留未来从“常用工具”演化到“工作流组合”的可能性。

## 4. 核心体验

### 4.1 添加工具

首页的主输入框同时承担搜索和粘贴入口：

- 输入普通文字时执行即时搜索。
- 输入或粘贴 URL 时显示“添加此工具”动作。
- 粘贴多条 URL 时进入批量确认页。

系统并行提取每个 URL 的标题、描述和 favicon，再使用 AI 推断用途分类。确认页逐项显示结果；用户可以修改标题、描述和分类，也可以移除不想保存的条目。

只有 URL 是必填信息。自动处理失败的条目使用域名作为标题并进入“未分类”，不阻断同批次的其他条目。

### 4.2 浏览与查找

首页由三个稳定区域构成：

1. 顶部品牌和低频设置入口。
2. 主搜索/粘贴输入框和按分类连续排列的完整工具集合。
3. 桌面端左侧页面大纲，显示“常用、各用途分类、未分类”及对应数量。

页面默认展示所有书签，不通过大纲筛掉任何分类。点击大纲条目只平滑滚动到对应分组；用户滚动内容时，大纲根据进入视口的分组自动高亮当前位置。“常用”是顶部快捷副本，工具仍保留在原分类中。

在移动端，页面大纲收进从左侧滑入的抽屉。页面左侧保留明确的目录入口并显示当前位置；选择条目后抽屉自动收起并滚动到对应分组。抽屉支持点击遮罩和 Escape 关闭、焦点锁定及焦点归还，不隐藏添加、搜索或打开工具等关键能力。

工具项显示 favicon、名称和一句用途描述。点击主体在新标签页打开工具。收藏、编辑和删除属于次级操作，仅在悬停、聚焦或移动端操作菜单中出现。

搜索覆盖工具名称、域名、描述和分类名，结果即时更新。搜索是唯一会临时隐藏不匹配工具的浏览操作；清除搜索后立即恢复全量分组。无结果状态提供清除搜索动作；空数据状态直接引导用户粘贴第一个 URL。

### 4.3 收藏常用

用户可以将任意工具标记为常用。常用工具在首页顶部单独展示，默认按最近打开时间排序；尚无打开记录时按加入常用的时间倒序排列。

打开工具时先在本地记录最近打开时间，再导航到目标 URL。记录失败不得阻止导航。

## 5. 视觉与交互方向

采用“编辑式工具台”而不是传统管理后台：

- 以浅色、略带暖意的中性色为主，单一高辨识度品牌色用于选中状态。
- 采用内容驱动高度的高密度工具面板，不设置用于填满视口的固定或最小内容高度。页面在最后一个分类结束，避免把无数据区域误表现为界面留白。
- 桌面端采用窄左侧大纲加双栏分类内容的不对称布局。每个分类是一个紧凑分组，书签在分组内双列排列；中小屏降为单栏分类，手机端书签降为单列。
- 标题、搜索和分组标题均保持紧凑单行。工具项以图标、名称和单行用途为主，长内容截断并通过可访问名称保留完整信息。
- 分类分组使用紧凑内边距和短间距建立节奏，不为数量不足的分类预留整行宽度，也不设置占据首屏的大型欢迎区或统计区。
- 搜索框是页面的视觉锚点；工具集合保持扁平，避免层层卡片嵌套。
- 字体层级清晰，工具名称优先于描述和元信息。
- 页面载入采用一次轻量的分段显现；交互反馈以状态变化为主，不使用弹跳动画。
- 所有可操作元素具备键盘焦点样式，颜色和文字对比满足 WCAG AA。
- 高密度不得牺牲操作性：桌面端工具项和按钮的点击高度不低于 40px，移动端主要操作目标不低于 44px。
- 移动端保留添加、搜索、大纲定位、收藏和打开功能；左侧大纲转换为可收起抽屉，不以隐藏关键操作换取空间。

已确认的概念稿保存在本地 Visual Companion 会话中，仅作为视觉参考，不纳入产品运行时依赖。

## 6. 系统架构与组件边界

沿用现有 TypeScript monorepo：

- `apps/web`：React 客户端，负责首页、搜索、添加确认和工具操作。
- `apps/api`：Express API，负责校验请求、协调元数据与 AI 服务。
- `packages/db`：SQLite 数据访问，负责工具、分类、设置和使用状态。
- `packages/shared`：前后端共享的类型和请求响应契约。

前端按职责拆分为：

- `HomePage`：组合页面区域和全局状态，不承载数据处理细节。
- `CommandInput`：识别搜索文本、单 URL 和多 URL 三种输入意图。
- `CategoryOutline`：桌面端展示分类大纲，移动端管理左侧抽屉，并同步内容滚动位置。
- `ToolCollection`：组织常用快捷区和按分类连续排列的完整工具集合。
- `ToolItem`：打开工具和呈现次级操作。
- `AddToolsFlow`：处理提取进度、逐项确认、修改和保存结果。

数据访问继续通过 hooks 封装，UI 组件不直接拼接 API 请求。API 路由保持轻量，将网页解析和 AI 分类委托给独立 service。

## 7. 数据模型

现有 `bookmarks` 表继续作为工具实体，增加：

- `is_favorite INTEGER NOT NULL DEFAULT 0`
- `favorited_at TEXT NULL`
- `last_opened_at TEXT NULL`

`is_favorite` 控制常用区展示，`favorited_at` 为无使用记录时提供稳定排序，`last_opened_at` 用于常用工具的最近使用排序。

现有分类模型保持单层分类。每个工具最多属于一个分类；MVP 不引入标签、多级目录或工具与分类的多对多关系。

## 8. 数据流

### 添加

1. 用户粘贴 URL。
2. 客户端完成 URL 提取、去重和基本格式校验。
3. API 并行获取元数据，并在可用时调用 AI 分类。
4. API 返回每条 URL 的独立结果与错误状态。
5. 用户确认或修改结果。
6. 客户端批量保存有效条目并刷新首页。

### 查找

MVP 数据规模按个人收藏设计，工具和分类一次加载到客户端。搜索在内存中完成，避免每次输入触发网络请求。分类大纲只负责锚点定位和滚动状态同步，不修改工具数据集合。

### 打开

1. 用户点击工具。
2. 客户端乐观更新最近使用状态，并向 API 发送记录请求。
3. 浏览器立即在新标签页打开 URL。
4. 记录失败仅回滚排序状态，不影响导航。

## 9. 错误处理

- 非法或不支持的 URL：在确认页就地标记，不发送保存请求。
- 重复 URL：同批次自动去重；数据库已有 URL 时提示并跳过，避免创建副本。
- 元数据失败：使用域名作为标题、空描述和默认图标。
- AI 不可用或分类失败：放入“未分类”，允许用户手动选择分类。
- 部分批量保存失败：保留失败条目和用户修改，展示逐项原因，并允许仅重试失败项。
- 网络或 API 不可用：首页继续展示已经加载的数据；写操作明确提示未保存，不伪装成功。
- 删除工具：需要明确确认；MVP 使用应用内确认区域，不依赖浏览器原生确认框。

错误消息说明发生了什么以及下一步能做什么，不暴露服务端堆栈、API 密钥或内部请求细节。

## 10. 测试策略

### 单元测试

- URL 提取、标准化和去重。
- 搜索匹配、分组排列与大纲当前项判定。
- 常用工具排序规则。
- 元数据失败和 AI 失败的降级结果。

### API 与数据库集成测试

- 单个和批量创建，包括部分失败。
- 重复 URL 处理。
- 收藏状态和时间字段更新。
- 最近打开记录。
- 无 API Key 时的分类降级。

### 前端交互测试

- 从空状态添加第一批工具。
- 搜索、清除搜索、大纲定位及滚动高亮。
- 收藏、取消收藏和排序变化。
- 编辑、删除与错误恢复。
- 键盘操作和移动端关键路径。

### 发布前端到端验收

使用真实可访问 URL 和故意失败的 URL，完整验证“粘贴—确认—保存—查找—收藏—打开”流程。运行现有构建、类型检查和 lint，且不得引入新的控制台错误。

## 11. MVP 范围边界

### 包含

- 单个与批量 URL 添加。
- 元数据提取和 AI 用途分类。
- 添加前确认与修正。
- 单层分类、全量分组展示、即时搜索和大纲定位。
- 常用收藏与最近打开排序。
- 工具编辑和删除。
- 本地 SQLite 持久化。
- 桌面和移动端响应式体验。

### 不包含

- 公共工具库、榜单、推荐流或社区内容。
- 账号系统、云同步、导入浏览器书签。
- 团队空间、权限和协作。
- 标签、多级目录和复杂拖拽编排。
- 工作流组合、一键打开多个工具。
- 浏览器扩展、原生客户端和离线应用。
- 使用统计仪表盘。

## 12. 实施约束

- 优先复用现有 API、数据库和 hooks；只对直接服务核心体验的部分重构。
- 数据库变更必须兼容已有安装并提供迁移逻辑。
- API Key 继续只保存在本地，不发送到非配置的第三方端点。
- 不以新增依赖代替可以在现有栈内清晰实现的功能。
- 单个组件保持单一职责；输入识别、数据处理和视觉呈现不得集中在一个大型页面组件中。
